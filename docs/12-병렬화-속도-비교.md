# 12. 추출 파이프라인 병렬화 전/후 속도 비교 (2026-08-04 실측)

한 줄 요약: **네트워크 왕복(이미지 확인·다운로드)을 동시 8개로 병렬화해
1,500개 사이클이 약 3시간 → 33분(약 5.5배, 82% 단축)이 됐다.** 선별 결과물은
순차 실행과 동일함을 보장한다.

## 1. 배경 — 시간이 어디에 쓰이고 있었나

계산(룰베이스 필터·점수화)은 수만 개 기준 1초 미만으로 공짜다. 실측상 시간의
정체는 전부 **네트워크 왕복을 순차로 기다리는 것**이었다:

- **선별(select)**: 후보 1개당 이미지 3장(정면·성분·영양라벨)의 생존 확인
  요청을 순차로 보냄 → 왕복 3번 × (0.3~0.5초 + 예의상 0.1초 대기) ≈ **개당 2.4초**.
- **빌드(build_fixtures)**: 신규 엔티티의 이미지 3장을 순차 다운로드 ≈ **개당 ~4초**
  (이미 받은 이미지는 캐시 재사용이라 0초).

## 2. 무엇을 바꿨나 (2곳, 각각 동시 8개)

| 위치 | 변경 | 결과 동일성 |
|---|---|---|
| `off_harvest.py` select | 생존 확인 요청을 32개 묶음으로 동시 8개 발사. 판정·기록(중복 키, 탈락 집계, 스냅샷 수정)은 **순위 순서대로 순차 소비** | 순차판과 선별 결과 동일 |
| `build_fixtures.py` | 본 루프 전에 "게이트 통과 예정 엔티티의 미보유 이미지"만 골라 동시 8개로 **프리페치**. 본 루프는 파일이 있으면 그냥 지나감. 프리페치 실패분은 본 루프가 재시도 → 안 되면 BUILD FAIL 보고(기존 안전망) | 산출물 동일, 검증 전 항목 통과 확인 |

요청당 0.1초 대기는 제거하고, 대신 **동시 8개 상한**으로 OFF 서버 예의를 유지한다.

## 3. 실측 비교

측정 조건: day-08 확장, 라운드=500개 선별, 체크포인트=finalize(팩트추출→빌드
×2→검증 2종→검수 리포트). 체크포인트당 신규 이미지 약 4,400장 다운로드.

| 구간 | 순차(전) | 병렬(후) | 배율 |
|---|---|---|---|
| 선별 1라운드(500개) | ~20분 (라운드 1~3) | **1분 36초~1분 47초** (라운드 4·6) | **~12×** |
| finalize 체크포인트(신규 1,500) | 118분 (체크포인트 1, 14:43→16:41) | **28분** (체크포인트 2, 16:49→17:17) | **4.2×** |
| 사이클 합계(1,500개) | ~3시간 | **~33분** | **5.5× (82% 단축)** |

- 체크포인트의 남는 28분도 대부분이 고정비(전체 팩트 재추출, 전체 페이지 재생성
  ×2벌, 검증 2종)라 코퍼스가 커질수록 늘어나는 부분이며, 이미지 구간 자체는
  ~100분 → ~13분이 됐다.
- 참고: 병렬 폭을 8보다 올리면 더 빨라지지만, OFF는 무료 공공 서버라 차단
  위험이 있어 8로 고정했다.

## 4. 한계·주의

- 병렬화는 **속도만** 바꾼다. 어떤 후보가 뽑히는지, 페이지·이미지 산출물은
  순차 실행과 동일하다(체크포인트 2에서 validate 전 검사·verify_batch로 확인).
- 프리페치는 게이트 판정식을 본 루프와 중복 보유한다(`build_fixtures.py`의
  주석 참조). **게이트 규칙을 바꿀 때는 두 곳을 같이 고칠 것.**
