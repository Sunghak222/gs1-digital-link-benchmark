## 1. DL 에이전트 상시 실패 — 수리 완료

- **증상**: external 경로의 마지막 단계(도구를 쥔 LLM 에이전트)가 매 질문 400 에러로 죽음.
  병렬 페이지 읽기가 먼저 문서를 확보해두는 덕에 **답은 정상으로 나와서 조용히 묻혀 있었음**.
- **원인**: `digital_link_raw_agent.py:61`이 OpenAI 호출에 `max_tokens`를 넘기는데
  gpt-5.4-mini는 `max_completion_tokens`를 요구.
- **조치**: 성학이 직접 수정(2026-07-13, 원 줄은 주석 보존). **팀 저장소 반영 필요** —
  이 폴더는 zip 스냅샷이라 git 이력이 없다.

## 2. `.env` `DIGITAL_LINK_RAW_AGENT_MAX_TOKENS=262144` — 수정 필요

- 1번 수리 후에도 에이전트가 400으로 죽음: 262,144가 모델의 **완성 토큰 한도 128,000 초과**.
  컨텍스트 창(400k)과 완성 상한을 혼동해 설정된 것으로 추정.
- 평가 실행은 환경변수 `DIGITAL_LINK_RAW_AGENT_MAX_TOKENS=128000` 덮어쓰기로 우회 중.
  **.env 값을 128000 이하로 수정 권장** (팀 판단 — 코어·설정은 팀 관할이라 평가 쪽에서 건드리지 않음).

## 3. JSON-LD 우선 추출이 본문을 폐기 — 수정 권고

- **동작**: 페이지 압축기(`agents/utils/mcp.py:182-188`)가 HTML에서 JSON-LD 블록을 발견하면
  **그것만 반환하고 나머지 본문 텍스트를 전부 버린다.**
- **실측 사례** (본실험 오답 6건, 전부 이 유형): 부산타워 pip.html — 본문에
  "120m 높이의 전망대"가 있으나 JSON-LD에는 이름뿐 → 파이프라인이 받은 건
  `{"name": "부산타워"}`가 전부 → "높이 정보가 없습니다"로 오답.
  (증거: `benchmark/results/20260713-164735_miss-original/failure-analysis.md`)
- **공정한 주석 — 벤치마크 마크업의 대표성**: 문제가 난 페이지(장소 pip 계열)의 JSON-LD는
  이름만 담고 있어 실세계의 잘 마크업된 Place(주소·좌표·영업시간 포함)보다 빈약하다 →
  **발생 빈도는 과대표집일 수 있음.** 그러나 실사이트에서도 산문 서술(역사·특징)은 본문에만
  있는 게 표준이므로, "JSON-LD가 내용을 충분히 커버하는지 확인 없이 본문을 버리는" 동작
  자체는 실환경에서도 손실을 낸다. (우리 벤치마크의 다른 T3 페이지들은 페이지 팩트를
  JSON-LD에 담고 있어 이 경로로도 정답이 나온다 — 43장 중 23장.)
- **권고**: JSON-LD를 버리지 말고 본문 추출 결과와 병합. 수정안을 로컬에서 구현·검증까지
  마쳤으나(본문 '120m' 생존 확인) **2026-07-14 사용자 지시로 원복** — 코어 수정은 팀 판단에
  맡긴다. 검증된 수정안: json_ld와 함께 본문 텍스트를 `text` 키로 유지 (기존 키 형식 불변).
- 벤치마크 쪽 메모: v1.1에서 pip 계열 JSON-LD 보강(주소·좌표 수준) 검토 — 단 지금 구성은
  이 결함을 드러내는 유용한 극단 사례이기도 하다.
- **같은 함수의 부수 동작** (참고, 경미): 길이 상한(~4,000자) **이하** 페이지는 HTML 추출
  없이 **태그째 원문으로 전달**된다 (mcp.py:189-199 — 추출은 상한 초과+HTML일 때만).
  ③-a 실측(감천 별명 문항)에선 원문이 통째로 도달해 오답 원인은 아니었음(순수 독해 실패로
  판정) — 토큰 낭비·노이즈 수준. JSON-LD 병합 수정 시 같은 함수라 함께 정리 권장.

## 4. 동시 요청 대비 없음 — 서비스화 전 필수 4건

한 요청 안의 자원 관리는 잘 돼 있으나(병렬 읽기, 백그라운드 벡터 작업), **요청들 사이에
공유되는 자원**의 관리가 없다. 동시 쿼리가 늘면:

| 위치 | 문제 | 권고 |
|---|---|---|
| `digital_link_explorer.py:604` | 병렬 읽기 세마포어가 **요청당** 생성 — 동시 10쿼리면 최대 80 동시 fetch, 전역 한도 없음 | 프로세스 전역 한도 (진짜 전역은 프록시/큐) |
| `agents/vector_jobs.py:162-165` | 작업 등록부(상한 64) 초과 시 **실행 중 작업도 등록부에서 제거** → 그 쿼리는 벡터 결과 없이 합성 — **에러 없이 품질만 저하** | done만 제거, 초과 시 신규 거부. **우선 수리 권장** (몇 줄) |
| `vector_index/retrievers/vector.py:341-346` | VLM 캐시 파일을 통째로 읽고-고치고-다시 씀 — 동시 쓰기 시 항목 유실(재과금), 비원자 쓰기라 깨지면 캐시 전체 증발 | 임시파일→`os.replace` + 락. **우선 수리 권장** |
| LLM 호출 전반 | 429(호출 한도) 지수 백오프 없음 — 쿼리당 5~8회 호출이라 동시성에 민감 | 백오프 재시도 |

## 6. KG 추출의 출처 기록이 사실상 "턴 단위" — 보고 대기 (2026-07-31 발견)

- **구조**: kg_builder는 답변 완성 후 **턴당 LLM 1회**로 KG 페이로드를 추출한다
  (kg_builder.py:119-141) — 그 턴의 검색 결과 전부(kg_result + external_result)와 최종
  답변을 한 프롬프트에 합쳐 넣는다. 따라서 한 관계가 여러 문서의 합성에서 나올 수 있다.
- **문제 3가지** (kg_builder.py 실측):
  1. **출처 도장 찍기**: 출처 목록(`source_references`)을 턴에서 한 번만 만들고
     (`_extract_source_references`, :628-653) **그 턴에 생성된 모든 관계에 같은 목록을
     통째로 복사**한다 (:586 → `_extensions_with_sources` :613-626). 관계 A는 문서 1,
     관계 B는 문서 2에서 왔어도 둘 다 전체 목록을 단다 — "관계 단위 출처"가 아니라
     "턴 단위 목록의 관계별 복사"다.
  2. **벡터 문서 누락**: 출처 목록은 `digital_link_result`에서만 추출(폴백은
     traversed_links) — 벡터 검색 문서에서 온 사실은 출처가 비거나 남의 출처를 단다.
  3. **누적 오염**: 같은 관계가 다른 턴에 갱신되면 기존+신규 출처가 병합·중복제거되어
     (:620-623) 시간이 갈수록 한 관계에 여러 턴의 출처가 쌓인다.
- **영향**: "원문이 바뀌면 어떤 사실을 무효화할까"를 현행 데이터로 풀면 그 턴의 관계
  전부를 죽이는 것 외에 방법이 없다 (docs/16 T1의 출처 굵기 사다리에서 조건 D(관계 단위)의
  실체가 실제로는 이보다 굵은 "턴 단위"임 — 실험 조건에 반영 예정).
- **권고**: LLM이 관계별로 근거 문서를 지목하게 프롬프트 스키마에 `source_urls` 필드를
  추가하고(관계 스키마 확장), 벡터 문서도 출처 후보 목록에 포함. 저장 전 실존 URL 검사
  (answer_synthesizer의 `prune_used_sources` 패턴 재사용)로 날조 차단. 코어 수정이므로 팀 판단.

## 부록 A — 벤치마크 데이터 쪽 발견: packaging 팩트의 linktype 매핑 (2026-07-14, 성학 지적)

- **사실**: OFF의 포장 재질(`packaging_tags`) 팩트 10개가 전부 `consumerHandlingStorageInfo`
  페이지에 인쇄돼 있고, 이를 근거로 하는 QA가 13개다.
- **판정 — 정의상 무리가 맞다**: GS1 웹 어휘에서 `consumerHandlingStorageInfo`는 소비자의
  **취급·보관 요령**(냉장 보관 등)이고, 포장 **재질**은 `gs1:recyclingInfo`(포장 재활용 정보)가
  정위치다. 우리 linktype 세트(6종)에 recyclingInfo가 없어서 추출 규칙이 가장 가까운 페이지에
  밀어 넣은 것.
- **평가에 미친 영향**: ③-a의 "후보 선택 실패" 14건 중 **8건이 전부 packaging 질문** —
  "packaging?"이라는 질문에 선택기가 storage 페이지를 안 고른 건 GS1 의미론대로면 오히려
  합리적 행동이라, 이 8건은 파이프라인 잘못으로 단정할 수 없다. 수치 해석 시 분리 보고.
- **재발 방지 (2026-07-14, 성학 아이디어)**: 규칙표 전수를 GS1 정의를 아는 LLM으로 블라인드

  1차 감사 결과: **손규칙 불일치 0건** — packaging이 유일한 오배치였음을 확인. 산문 채굴
  팩트 34건의 "masterData가 낫다" 의견은 설계 의도(값을 산문에 묻어둠)와의 충돌이라 현행
  유지 (판독: `work/notes/linktype-audit.md`).
- **조치 완료 (2026-07-14, 성학 승인)**: `recyclingInfo` 페이지 신설 + packaging 팩트 10개
  이동 (extract_facts.py 규칙 1줄 + 페이지 라벨). 양쪽 코퍼스 재빌드, validate 전 항목 통과.
  총 페이지 120→123 (재활용 +10, 포장만 있던 보관 페이지 7개 소멸). qa.jsonl 무변경 —
