# 07 — OFF 전체 데이터 내려받기(덤프) 활용 계획

> 작성: 2026-07-16. 배경: 매일 10+10 확장 루틴(1일차 완료)이 커지면 API 호출 제한
> (상품 조회 분당 15회)에 부딪히고, OFF 공식 방침도 "수백 개 이상은 덤프를 써라"이다.
> 크기 수치는 2026-07-15 HTTP 헤더로 실측.

## 0. 요약

- 전체 데이터 파일은 **압축 상태로 12.5 GB** (JSONL) — 통째로 풀지 않고 **압축된 채로
  한 줄씩 흘려 읽는다**(스트리밍). 디스크에 12.5 GB 한 번만 쓰면 되고, 메모리는 몇 MB면 된다.
- 후보 고르기는 가벼운 **CSV판(1.3 GB)** 으로, 최종 스냅샷 저장은 JSONL판에서.
- 읽어들인 제품은 **지금의 API 스냅샷과 똑같은 파일 형태**(`data/raw/off/product-<바코드>.json`)로
  저장한다 → 추출부터 뒤 단계(팩트 추출→빌드→검증→QA)는 **코드 수정 없이 그대로** 돈다.
- 사진은 덤프에 없다 — 바코드로 URL을 만들어 개별 다운로드 (정적 서버라 API 제한과 무관).

## 1. 파일 크기 (실측)

| 파일 | 압축 크기 | 내용 | 용도 |
|---|---|---|---|
| `openfoodfacts-products.jsonl.gz` | **12.5 GB** | 전 제품(수백만 개)의 전체 필드, 한 줄 = 제품 하나 | 스냅샷 생성 (전체 필드 필요) |
| `en.openfoodfacts.org.products.csv.gz` | **1.3 GB** | 주요 필드만 표 형태 | 후보 선별·점수 계산 |

- 내려받기 주소: `https://static.openfoodfacts.org/data/` (매일 갱신, S3로 리다이렉트)
- 압축을 풀면 수십 GB지만 **풀 일이 없다** — gzip은 스트리밍 해제가 되므로(§3) 압축 파일만 보관.
- 보관 위치: `data/dump/` (이름에 받은 날짜를 붙인다: `openfoodfacts-products-20260716.jsonl.gz`).
  받은 날짜가 곧 데이터 기준일 — 스냅샷의 재현성 기록과 같은 원리.

## 2. 언제 전환하나

| 방식 | 적합 규모 | 제약 |
|---|---|---|
| 지금(API 호출 + 캐시) | 하루 10개 (호출 ~10회) | 분당 15회 제한 — 매일 배치엔 충분 |
| 덤프 스트리밍 | 하루 수십 개 이상, 또는 후보 풀을 크게 새로 짤 때 | 12.5 GB 1회 다운로드 (약 30분~1시간) |

당장 급하지 않다 — 매일 10개는 API로도 여유. 전환 시점은 ① 후보 풀을 수백 개 규모로
다시 뽑고 싶어질 때, ② 하루 배치를 20개 이상으로 늘릴 때, ③ OFF가 느려지거나 막힐 때.

## 3. 처리 방법 — 압축된 채로 한 줄씩

핵심 도구는 **이미 구현돼 있다**: `scripts/clients/off_client.py`의 `stream_dump()` —
gzip을 열어 한 줄(제품 하나)씩 JSON으로 풀어 내보내고, `fields`를 주면 필요한 칸만 남겨
메모리를 평평하게 유지한다. 깨진 줄은 건너뛴다.

```python
# 전량 훑기: 12.5 GB를 메모리 몇 MB로 (1회 순회 ≈ 수십 분, 디스크 속도에 좌우)
for rec in off_client.stream_dump(DUMP, fields={"code", "product_name", "lang",
                                                "nutriments", "image_nutrition_url", ...}):
    ...
```

### 3.1 두 단계 파이프라인

**1단계 — 후보 선별 (CSV판, 판다스 몇 분)**
CSV를 청크로 읽어 지금의 풍부도 점수(`score_food` — prepared 제외 반영됨)를 그대로 적용:
국가·언어(lang=en)·바코드 유효성(체크숫자)·사진 3종 보유·영양성분 10칸+ 를 걸러
**목표의 3~5배 후보 목록**(바코드 리스트)을 만든다. → `work/candidates-food.jsonl` 형식 그대로.

**2단계 — 스냅샷 추출 (JSONL판, 1회 순회)**
후보 바코드를 집합(set)으로 들고 JSONL 덤프를 한 번 훑으며, 일치하는 줄만
`data/raw/off/product-<바코드>.json`으로 저장한다 — **API가 돌려주던 것과 같은 봉투 구조로
감싸서** 저장하면 기존 `get_product()` 캐시와 구분이 없어진다. 이후 단계는 무수정.

주의: 덤프 1회 순회로 **후보 전부**를 한꺼번에 뽑는다 (매일 10개씩 여러 번 순회하지 않는다 —
순회 1번이 수십 분이므로). 즉 "덤프 받는 날 = 후보 수백 개 스냅샷을 미리 쟁여두는 날"이고,
매일 배치는 쟁여둔 스냅샷에서 10개씩 꺼내 쓰면 된다.

**사진 (별도)**
덤프에는 이미지 파일이 없고 URL 규칙만 있다. 바코드로 URL을 만들어
(`images.openfoodfacts.org/images/products/<바코드 경로>/...`) 정면/영양라벨/성분 사진 3장을
내려받는다. 정적 파일 서버라 분당 15회 제한과는 별개지만, 수백 장이면 0.5~1초 간격을 두고
예의 있게 받는다. 기존 저장 경로·이름 규칙 그대로.

### 3.2 검증

- 표본 대조: 덤프에서 뽑은 제품 5개를 API `get_product()`로도 받아 주요 필드 일치 확인
  (덤프는 하루 전 상태일 수 있음 — 불일치가 크면 그 제품은 API 값을 채택).
- 기존 20개 식품은 재추출하지 않는다 — v1.0 동결 원칙. 덤프 경로는 신규 후보에만 쓴다.

## 4. 유의점

| 항목 | 내용 |
|---|---|
| 디스크 | 12.5 GB + CSV 1.3 GB. 외장/여유 공간 확인. 오래된 덤프는 새 덤프 받으면 삭제 |
| 시간 | 다운로드 30분~1시간 + 전량 순회 수십 분 — 하루 배치와 분리해 "쟁여두기 날"에 실행 |
| 기준일 | 파일명에 받은 날짜 기록. 논문에는 "OFF 덤프 YYYY-MM-DD 기준" 한 줄 명시 |
| 라이선스 | ODbL 그대로 적용 — 덤프를 쓴다고 달라지는 것 없음 (share-alike, 출처 표기) |
| 한국 식품 | 덤프를 다 뒤져도 한국 제품 데이터 빈약은 그대로 (OFF 자체의 한계) — 이 축은 다른 소스 검토 필요 |
| User-Agent | 덤프 다운로드·사진 다운로드에도 앱명/연락처 User-Agent를 붙인다 (OFF 요구사항) |

## 5. 구현 체크리스트 (전환 결정 시)

1. `scripts/fetch_dump.py` (신규, ~50줄): 날짜 붙여 다운로드 + 이어받기 + User-Agent
2. `select_entities.py`에 `food-dump` 서브커맨드: CSV 청크 → 기존 점수식 → 후보 3~5배 목록
3. `scripts/snapshot_from_dump.py` (신규, ~60줄): 후보 set → JSONL 1회 순회 → API 봉투로 저장
   + 사진 3종 다운로드 (간격 두기)
4. 표본 5개 API 대조 검증 → 이후 매일 배치는 기존 루틴 그대로
