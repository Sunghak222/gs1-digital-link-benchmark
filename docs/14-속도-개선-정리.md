# 14. 파이프라인 속도 개선 총정리 (2026-08-04 ~ 08-05)

이틀에 걸쳐 추출·빌드 파이프라인의 느린 곳을 잡았다. 결과만 먼저:

| 작업 | 고치기 전 | 고친 후 |
|---|---|---|
| 후보 500개 고르기 (1라운드) | ~20분 | **1분 반** |
| 팩트 뽑기 (전체) | 7~10분 | **27초** |
| 페이지 만들기 (전체) | ~20분 | 처음 한 번 69초, **이후 9초** |
| 검사 (validate) | 70초 | **27초** |
| 마무리 작업 한 사이클 (finalize) | ~2시간 | **~5분** |

코드를 뜯어고친 게 아니라, 거의 전부 "**쓸데없이 반복하던 일을 안 하게**" 만든 것이다.
아래는 뭐가 문제였고 어떻게 고쳤는지를 하나씩 푼 것.

## 1. 왜 느렸나 — 세 가지 패턴

느린 원인을 다 파보니 결국 세 부류였다.

**패턴 A. 매번 똑같은 준비를 처음부터 다시 함**
- 팩트 하나하나가 "형식에 맞는지" 확인할 때, 확인용 검사 도구를 **팩트마다 새로
  조립해서** 썼다. 한 번 조립해 두고 35만 번 돌려쓰면 12초인 일을, 35만 번 새로
  조립하느라 17분을 썼다. 팩트 추출이 7~10분 걸린 이유의 사실상 전부가 이거였다
  (진짜 "추출"은 3초짜리였다).
- 후보를 고를 때 "이미 뽑은 목록"과 대조하는데, 그 대조용 목록을 **후보 한 명
  볼 때마다 처음부터 다시 만들었다**. 후보 1.6만 × 기선정 2만 → 헛일 수억 번.
- 서버에서 이미지를 받을 때 **요청마다 연결을 새로 텄다**(전화 걸 때마다
  번호부터 다시 누르는 격). 연결을 한 번 트고 계속 쓰도록 바꿈.

**패턴 B. 안 바뀐 것까지 전부 다시 만듦**
- 페이지 빌드가 매번 **코퍼스 전체를 다시 굽는** 구조였다. 새로 온 2천 개만
  구우면 되는데 2만 개를 다 다시 만들었다. 이제는 엔티티마다 "재료(팩트·이미지
  목록)가 지난번과 같은가"를 기록해 두고, 같으면 그냥 지난 결과를 쓴다.
  단, 페이지 만드는 **규칙 자체를 고쳤을 때는** 코드 안의 버전 표시
  (`BUILD_RULES_VERSION`)를 올려야 전체를 다시 굽는다 — 이거 잊으면 옛 엔티티에
  새 규칙이 반영 안 되니 주의.
- 팩트 추출이 매번 만들던 105MB짜리 "사람 열람용 사본"(facts.pretty.json)도
  필요할 때만(`--pretty`) 만들게 바꿈.

**패턴 C. 한 번만 하면 됐던 청소가 상시 업무로 눌러앉음**
- 예전에 이미지 포맷 버그를 고치면서 "기존 파일도 한 번 손보자"고 넣었던 코드가
  그대로 남아, **매 빌드마다 이미지 4만 장을 전부 열어 재검사**하고 있었다.
  빌드 시간의 대부분이 사실 이거였다.
- 스냅샷 단계에도 같은 부류("영양정보 빈 파일 치유")가 하나 더 있어서 같이 제거.

셋 다 공통점: **엔티티 20개 시절엔 비용이 0이라 아무도 못 느꼈다.** 코퍼스가
1,000배가 되는 동안 코드가 그대로였고, 커진 뒤에야 청구서가 날아온 것.

## 2. 네트워크 기다림은 겹치기와 동시 진행으로

계산이 아니라 "기다림"이 문제인 곳은 없애는 게 아니라 겹치게 했다 (docs/12 상세):

- 이미지가 살아있는지 확인하는 왕복, 이미지 내려받기 → **한 번에 8개씩 동시에**
  (서버 예의를 위해 8개 상한).
- 내려받기는 후보 고르는 동안 **뒤에서 미리** 해 둔다(media_prefetch). 마무리
  단계가 시작될 땐 이미지가 이미 다 있다.
- 죽은 이미지(404)는 예전엔 "혹시나" 하고 3번 더 두드리고 사이사이 12초를
  기다렸다 → 죽은 건 **바로 포기**하고 넘어간다. 재시도는 서버가 바쁘다는
  신호(일시 오류)일 때만.

## 3. 이번에 고친 목록 (한 줄씩)

| # | 위치 | 내용 |
|---|---|---|
| 1 | extract_facts | 형식 검사 도구 1회 조립 후 재사용 (7~10분→27초) |
| 2 | validate | 같은 문제 + 한글 페이지 검사를 장소에만 + 경고 3.9만 줄 출력을 요약 1줄로 (70→27초) |
| 3 | build_fixtures | 안 바뀐 엔티티 재사용(증분), 이미지 전량 재검사 제거, 실패 정리 방식 개선 |
| 4 | off_harvest | 기선정 대조 목록 1회 구축, 스냅샷 1.9만 파일 재읽기를 캐시로, 일회성 치유 코드 제거, 중복 확인을 파일 읽기보다 먼저 |
| 5 | fetch (공용) | 연결 재사용, 죽은 주소 즉시 포기, 마지막 실패 후 헛기다림 제거 |
| 6 | gen_qa | 형식 검사 도구 재사용, 49MB 목록 파일 이중 읽기 제거 (QA 대량 생성 대비 선제) |
| 7 | tour_harvest | 4번과 같은 패턴 한 곳 사전 제거 (장소 확장 커지면 터질 자리) |
| 8 | extract_facts | 열람용 105MB 사본은 요청 시에만 |

## 4. 일부러 안 고친 것

- **QA 생성기의 멀티홉 문제**: 같은 브랜드 제품끼리 묶는 문항이 브랜드 그룹
  크기의 제곱으로 불어나고, Tesco처럼 549개짜리 그룹은 "같은 브랜드의 다른
  제품은?"의 답이 548개가 되어 문항 자체가 성립하지 않는다. 성능이 아니라
  **설계 결정**이 필요해서 QA 착수 때(docs/17) 함께 정한다.
- 같은 파일에서 **이미지 문항 표시가 아예 동작하지 않는 버그**도 발견 — QA 때 수정.
- 재스캔 시 13GB 덤프를 처음부터 다시 훑는 구조 — 재스캔은 가끔이라 후순위.
- 자잘한 마이크로 최적화 — 잰 결과 티가 안 나는 것들은 손대지 않았다.

## 5. 교훈

1. **크기가 1,000배가 되면 코드를 다시 의심하라.** 오늘 잡은 것 전부가 "작을
   땐 공짜였던 코드"다. 느낌으로 "원래 오래 걸리는 일"이라 넘기지 말고, 실제로
   시간이 어디에 쓰이는지 재봐야 한다 — 팩트 추출 7분의 정체가 추출이 아니라
   검사 도구 조립이었던 것처럼, 잰 결과는 직관과 자주 다르다.
2. **"한 번만 돌릴 청소 코드"는 반드시 빼거나 격리하라.** 두 건이나 상시 경로에
   눌러앉아 있었다.
3. 병렬화보다 **"안 해도 되는 일 찾기"가 먼저다.** 이틀간 얻은 개선의 대부분은
   동시 실행이 아니라 중복 제거에서 나왔다.
