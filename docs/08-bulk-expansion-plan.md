## 1. 용어 먼저

- **덤프**: OFF가 매일 배포하는 전체 데이터 파일. 우리는 2026-07-20자 확보(`data/dump/`, CSV 1.2GB + 전체필드 JSONL 12GB)
- **스냅샷**: 제품 하나의 원본 데이터를 `data/raw/off/product-<바코드>.json`에 저장한 것. 이후 모든 단계가 이 파일만 읽으므로 "그때 소스가 뭐라 했는지"의 기록이자 재현성의 근거
- **게이트**: 후보를 통과/탈락시키는 자동 검사 규칙
- **선별**: 게이트 통과자 중에서 다양성을 고려해 최종 N개를 고르는 것

## 2. 파이프라인 설계

### 2.1 식품 (OFF 덤프) — 네트워크 의존 최소, 하루에 몇백 개 가능

```
[1] CSV 스캔(453만 행, 수 분)
      게이트: states=complete + 영어권 국가 + 바코드 체크숫자
              + 영양라벨 사진 + 성분 텍스트 + as-sold 영양 8칸 이상
      → 후보 바코드 목록 (실측: US/UK 기준 1,149개)
[2] JSONL 1회 순회(12GB, 수십 분)
      후보 바코드의 전체 레코드 추출 → lang=en 필터(★CSV엔 없고 JSONL엔 있음
      — 7/20의 "API 재검증" 단계가 통째로 사라짐) → API와 같은 봉투로 스냅샷 저장
[3] 위생·중복 게이트 (스냅샷 기준)
      기존 엔티티 바코드 제외, (브랜드+제품명) 정규화 동일 제외(하인즈 재발 방지),
      카테고리 en:null 오염 제외, prepared-전용 영양 제외, 플레이스홀더 값 필터
[4] 이미지 생존 확인
      front/nutrition/ingredients URL에 HEAD 요청 — 죽은 URL이면 탈락
      (빌드 단계에서 터지는 것을 선별 단계로 앞당김)
[5] 다양성 선별
      카테고리별 상한(예: 동일 1차 카테고리 최대 10%), 브랜드 쌍(멀티홉 재료) 확보,
      점수순 + 상한 규칙으로 N개 확정 → selection.yaml 끝에 추가
```

호출 예산: **0회** (덤프+스냅샷만. 이미지 HEAD는 이미지 서버라 API 한도와 무관).

### 2.2 장소 (TourAPI) — 호출 한도가 병목, 한도 인지형 + 이어달리기 설계

```
[1] 전국 목록 수집 (~140회, 싸다)
      areaBasedList2를 시도별 × 100행씩 전부 — 전국 관광지 12,680곳의
      기본 정보(이름·주소·좌표·대표사진 유무) 확보. 하회마을 사례 대비로
      키워드 시드 검색 병행
[2] 우선순위 정렬 (호출 0회)
      목록의 공짜 신호로 정렬: 대표사진 있음(사진 존재 가능성), 주소 완결,
      기존 엔티티 제외, 지역·유형 균형 가중치
[3] 상세 평가 (장소당 3회 — 예산의 대부분)
      detailCommon2(소개글) + detailIntro2(운영정보) + detailImage2(사진+저작권)
      게이트: 소개글 300자 이상 + KOGL Type1 사진 3장 이상 + 주소
      ★호출 카운터 내장: 한도 임박 시 우아하게 중단, 상태 파일 저장
[4] 다음 날 이어서 (같은 명령 재실행)
      캐시 덕에 이미 평가한 곳은 호출 0회 — 자동으로 이어달리기
[5] 다양성 선별 → GLN 채번(selection.yaml 순서, 끝에만 추가) 
```

호출 예산 실측 근거 (오늘 조사):
- 전국 목록: 12,680곳 ÷ 100 ≈ **127회** + 시도별 페이지 오버헤드 ≈ 140회
- 상세 평가: 1일차 (1,000−140) ÷ 3 ≈ **287곳**, 2일차부터 ~333곳/일
- 게이트 통과율 **23%** (표본 30곳 실측: 소개글 80% × Type1 사진 33%)
- → **1일차 약 65곳, 이후 일 75곳씩 누적**. 장소 300곳이 목표면 **약 4일** 소요
  (같은 명령을 나흘 반복 실행하면 됨 — 캐시·상태 파일이 이어달리기 보장)

### 2.3 공통 후처리 (기존 도구 그대로, 순서만 자동화)

```
extract_facts --verify-images  →  build_fixtures(원본+변조본)  →  validate
→  audit_linktype_mapping  →  verify_batch(전수 검증 스위트)  →  검수 리포트 생성
```

마지막 산출물 = **`work/expansion/<batch>/entity-review.md`** (오늘 day-02에 수동으로 만든
그 형식의 자동판): 엔티티 표 + 자동으로 잡아낸 애매 항목(채굴 표기 상이, 특이값,
분포 편중 경고) + 통계. 사용자는 이 파일만 훑으면 됨.

## 4. 공개 벤치마크 품질 — 지금 부족한 것

데이터 자체보다 **법적 표기와 문서화**가 공개의 관문이다.

1. **출처표시(attribution) 자동 생성** — 지금 manifest에 라이선스 한 줄뿐.
   - 공공누리 1형은 출처 표시가 **의무**: 장소 사진·텍스트마다 "한국관광공사 TourAPI" 표기
   - OFF는 데이터=ODbL(share-alike), 사진=CC-BY-SA(기여자 저작) — 제품별 OFF 페이지 링크 표기
   - → 빌드 시 `ATTRIBUTION.md` 자동 생성 (엔티티→소스→라이선스→링크 표), manifest에 미디어별 `license`/`provider` 필드 추가
2. **ODbL share-alike 명시** — 식품 파생 데이터(facts)는 ODbL 조건 승계를 README에 명시해야 함
3. **데이터 기준일 고정** — 스냅샷·덤프 날짜를 README와 run 기록에 명시 (이미 파일명에 있음 → 문서로 승격)
4. **재현 명령의 완결성** — 새 벌크 스크립트까지 README 재현 절차에 포함
5. (데이터 품질 측면은 기존 validate 7종 + 유일 배치 + CF 발산 검사로 이미 공개 수준 — 추가 불요)

## 5. "두 번 반복 안 하기" — 지난 배치에서 데인 함정 13개를 전부 게이트로

배치 2번(7/15, 7/20)에서 한 번씩 데이고 임시로 고쳤던 것들이다. 대량 확장 코드에는
처음부터 전부 내장해서 같은 문제를 세 번째로 만나지 않는다.

### 식품(OFF) 소스의 함정

1. **CSV에는 언어 정보가 없다** (7/20) — CSV로 뽑은 상위 후보 35개 중 26개가
   프랑스어·이탈리아어 제품이었다. CSV 211칸에 `lang`이 없어서 거를 수 없었고
   그날은 제품 API를 일일이 다시 불렀다. → JSONL(lang 있음)에서 스냅샷 뜨는
   단계에 언어 필터 내장. API 재확인 단계 자체가 사라짐 (§2.1[2]).
2. **분말 제품의 영양성분** (Nesquik, 7/15) — 영양수치가 전부 "타 먹었을 때"
   기준(prepared)이고 제품 자체 수치가 없어 영양 페이지가 텅 비는 경우.
   → 점수 계산에서 prepared 칸 제외(반영됨), 벌크 게이트에 승계.
3. **카테고리 오염** (Dulano, 7/20) — 카테고리 값이 문자 그대로 `en:null`.
   카테고리는 다양성 선별의 기준이라 오염되면 선별이 왜곡 → 게이트에서 제외.
4. **동명 제품 중복** (Heinz, 7/20) — 기존 엔티티와 같은 이름의 다른 바코드
   (다른 시장판). 규칙: **(브랜드+제품명) 정규화 동일이면 제외, 브랜드가 다르면
   동명 허용** (Pip&Nut vs Meridian 사례 — 바코드가 구분해 주므로, 사용자 결정).
5. **"없음"이 글자로 들어있는 값** (7/20) — 원산지 칸의 "Not indicated." 등이
   팩트로 저장돼 QA 정답이 되는 문제 → `_JUNK_VALUE` 필터(반영됨).
   주의: **알레르겐/traces의 "none"은 "알레르겐 없음"이라는 의미 있는 사실**이라
   지우면 안 됨 — 실제로 같이 지웠다가 복구한 전력 있음.

### 장소(TourAPI) 소스의 함정

6. **저작권 검사가 늦으면 낭비** (7/20) — KOGL 필터가 빌드에만 있어서 선별 때
   "사진 6장"으로 뽑힌 곳이 빌드에서 전부 걸러져 사진 부족이 되던 문제
   → 선별 게이트가 "Type1 사진 3장 이상"을 직접 센다 (빌드 필터는 이중 방어로 유지).
7. **딱지 회색지대** (7/21 결정) — 저작권 코드 미기재 사진, 대표사진(firstimage,
   코드 확인 불가)은 공개 배포 기준으로 위험 → **명시적 Type1만 사용**.
8. **확장자 거짓말** (성산일출봉, 7/9) — URL은 .jpg인데 실제 BMP, VLM이 거부
   → `_to_jpeg`가 실제 바이트 기준으로 변환(반영됨).
9. **값에 섞인 HTML 찌꺼기** (7/21) — 운영시간 값의 `<br>` 태그가 QA 정답을
   오염 → `_strip_br` 필터(반영됨).

### 파이프라인 자체의 함정

10. **특이값을 사람이 사냥하게 하지 않기** — "Cheorwon vs 철원" 표기 문제가
    로그에만 남아 사용자가 되물어야 했음 (7/20~21) → 검수 리포트 생성기가
    표기 상이·특이값·분포 편중을 자동 검출해 항상 파일로 전달.
11. **GLN 채번은 순서가 생명** — GLN은 selection.yaml의 줄 순서로 채번된다.
    중간 삽입/삭제가 일어나면 뒤 장소들의 번호가 전부 밀려 기존 페이지·QA·실험
    기록이 조용히 다른 장소를 가리키게 됨 → append 전에 기존 순서 해시 대조 assert.
12. **죽은 이미지 URL** — 덤프 기준일 이후 삭제된 사진이면 빌드 단계에서 터짐
    → 선별 단계에서 HEAD 요청으로 생존 확인 (§2.1[4]).
13. **gen_qa 캐시가 옛 답을 돌려주는 지뢰** (7/21 발견) — QA 초안 LLM 캐시 키가
    팩트 "개수"만 봐서, 값이 바뀌어도 개수가 같으면 옛 값으로 만든 초안을 재사용
    → 키에 팩트 값 해시 포함 (§6 선행 수정).

## 9. 리스크·한계

- **표본 오차**: 장소 통과율 23%는 표본 30곳 기준(신뢰구간 대략 10~40%) — 1일차 실제 수율로 재보정
- **TourAPI 불안정**: 응답 지연·간헐 오류 잦음 — 재시도+캐시로 흡수, 하루 수율이 계획보다 낮을 수 있음
- **덤프 신선도**: 20260720 기준 — 그 이후 수정·삭제된 제품이 섞일 수 있음(이미지 생존 확인이 부분 방어). 공개 시 "기준일" 명시로 해소
- **VLM 라벨 대조 비용**: 식품 300개 × gpt-4o-mini 사진 판독 ≈ 수 달러 수준 (실행 전 파일럿 10개로 실측 후 진행)
- **검수 축소의 대가**: QA 단계를 미루더라도, 엔티티 품질 문제가 QA 생성 때 뒤늦게 드러날 수 있음 — entity-review.md의 자동 검출 항목을 계속 보강하는 것으로 상쇄
- **v1.0 동결 유지**: `releases/v1.0/` 무접촉. 대량 확장분은 v1.1+ 트랙
- **매일 누적 시 빌드·검증 시간 증가**: 현재 build_fixtures/validate는 매번 전체
  재실행(O(전체 엔티티)) — 1,000개 넘으면 회당 수십 분대 예상. Day 0 구현에
  **증분 모드**(신규 엔티티만 빌드, validate는 신규+주기적 전체) 포함
