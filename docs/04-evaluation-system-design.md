# 04 — 평가 시스템 설계 (v3)

> 작성: 2026-07-10 · v2: KG miss/hit 반영 (2026-07-10 팀 협의) ·
> **v3: 실그래프 실행으로 전환 + critic 평가 포함 (2026-07-13 결정 — "최대한 현실 성능을 잰다")**
>
> 벤치마크 데이터셋(01~03 문서)이 **시험지와 정답지**라면, 이 문서는 그 시험을
> **치르고 채점하는 프로그램** — 평가 시스템 — 의 설계다.
>
> 대원칙 세 가지:
> 1. **파이프라인 코드를 고치지 않는다.**
> 2. **벤치마크 데이터도 고치지 않는다.**
> 3. **실서비스 경로를 최대한 그대로 태운다** — 대체하는 것은 단 하나, "문서가 오는 곳"뿐 (§1).
>
> 용어: qa.jsonl의 필드명 `gold_answer`/`gold_fact_ids`는 표준 용어라 그대로 두고,
> 이 문서의 글과 지표 이름에서는 **정답**이라고 쓴다.

---

## 용어 먼저

| 용어 | 뜻 |
|---|---|
| **그래프** | 파이프라인의 실행 흐름도. 노드(부품) 9개가 화살표로 연결돼 있고, 질문 하나가 들어오면 화살표를 따라 흐른다 (state_graph.py:57-97) |
| **critic** | 답변을 검사하는 노드. "이 답으로 충분한가, 아니면 다른 경로를 더 시도할까"를 **LLM이** 판단한다 |
| **external 경로** | KG에 답이 없을 때 밖에서 문서를 가져오는 경로: linkset 조회 → 후보 링크 선택 → 페이지 읽기·인덱싱 → 벡터 검색 |
| **인덱싱** | 문서를 잘게 잘라 검색 가능한 형태로 DB에 넣는 작업 |
| **KG-miss / KG-hit** | 지식그래프(KG)가 **비어 있는** 상태(문서를 읽어야 답이 나옴) / **미리 채워져 있는** 상태(KG 조회로 바로 답함) |
| **CF (counterfactual)** | 값을 일부러 바꿔 만든 **변조 문서셋**. "외운 답"과 "읽은 답"을 구별하는 장치 |
| **TTFA** | Time To First Answer — 질문부터 답변까지 걸리는 전체 시간 |
| **캐시 채움 / 캐시 비움** | 이미지 설명(VLM) 캐시가 차 있는 상태(재사용, 빠름) / 빈 상태(첫 스캔 재현, 느림). 결과 폴더 라벨로만 warm/cold 표기 |
| **p50 / p95** | 여러 번 잰 시간을 줄 세웠을 때 가운데 값 / 상위 5% 경계값 ("보통은 이 정도, 느릴 땐 이 정도") |

## 0. 무엇을 재나 / 안 재나

모든 지표를 **KG 상태 2가지에서** 측정한다 (2026-07-10 팀 결정):

- **KG-miss**: 빈 KG — 실서비스에서 상품을 **처음 스캔해 질문한 순간**에 해당
- **KG-hit**: Neo4j KG에 벤치마크 팩트를 미리 적재 — 백그라운드 KG 적재가 끝난 뒤
  **다시 질문한 순간**에 해당

이 둘이 실제 제품 시나리오와 정확히 겹친다: 코어 파이프라인은 답변 후 백그라운드로 KG를
쌓기 때문에(state_graph.py:164 `_schedule_kg_builder`), "첫 질문 = miss, 나중 질문 = hit"이
실서비스의 자연스러운 흐름이다. miss vs hit 비교 = **"KG가 쌓이면 뭐가 좋아지는가"**의 정량화.

| 궁금한 것 | 지표 | 어떻게 확인하나 |
|---|---|---|
| 검색이 맞는 문서를 찾았나 | answer_page_hit@k (miss 전용) | manifest의 "이 팩트는 이 페이지에 인쇄됨" 기록과 대조 |
| 읽고 답을 맞혔나 | 답변 정확도 (LLM 채점) — 문서/이미지·언어·난이도별로 쪼개서 | qa.jsonl의 정답과 비교 |
| **진짜 읽고** 답했나, 외운 걸 답했나 | CF 발산율 (miss 전용, §4.3) | 원본·변조 문서셋에 같은 질문 → 답이 갈리는지 |
| **critic이 제대로 판단하나** | 조기종료율(miss) · KG답 거부율(hit) · 재시도 분포 (§4.4) | 문항별 critic 플래그·실제 경로 기록 |
| 얼마나 빠른가 | TTFA, 노드별 분해, **miss vs hit 격차** | 코어 계측(usage_metrics) 그대로 (§5) |

**안 재는 것**: 실세계 정확도(정답의 기준은 어디까지나 우리 문서셋),
적재값과 문서값이 어긋난 상황(오래된 KG, "stale") — phase 2 (§9).

## 1. 실행 방식 — 실그래프를 그대로 돌린다 (2026-07-13 결정)

### 1.1 무엇이 바뀌었나

v2까지는 "노드를 직접 조합"하는 방식이었다(라우팅·외부조회를 평가 시스템이 대신).
**v3부터는 진짜 그래프를 agent 모드로 통째로 돌린다** — 문항마다 `graph.ainvoke()`.
이유: 평가 목표가 "최대한 현실 성능"이므로,

- **TTFA가 진짜가 된다** — miss일 때 실서비스가 항상 지불하는 "KG 헛걸음"
  (retrieve_kg_1 → synthesize_1 → critic_1) 비용까지 포함된다.
- **critic이 측정 대상이 된다** — critic은 규칙 코드가 아니라 LLM 판단(critic.py:16-36)이라
  오판할 수 있고, 그 오판이 곧 현실 성능의 일부다 (§4.4).
- **후보 선택·병렬 페이지 읽기·이미지 분석·인덱싱까지** external 경로의 로직 전체가
  실경로 그대로 측정된다.
- **계측이 공짜다** — 그래프의 모든 노드가 이미 `ObservedNode`(metrics.py:186)로 감싸져
  있어, 노드별 시간·LLM 호출별 토큰이 `usage_metrics`에 자동으로 쌓인다.
  평가 시스템이 타이머를 하나도 만들지 않는다.

실서비스에서 KG-miss 질문이 흐르는 경로 (이걸 그대로 잰다):

```
format_query → retrieve_kg_1(빈손) → synthesize_1("확인 중입니다") → critic_1("부족해")
  → external 경로: linkset 조회 → 후보 링크 선택(LLM) → 페이지 병렬 읽기·인덱싱·벡터 검색
  → collect_vector_result → synthesize_2(문서 기반 답) → critic_2 → 끝
```

KG-hit이면 retrieve_kg_1이 팩트를 물어오고, critic_1이 수락하면 synthesize_1 답으로 끝난다.

### 1.2 대체하는 것은 단 하나 — 문서가 오는 곳 (로컬 도구 주입)

코드 확인 결과, 파이프라인의 외부 접근은 **`resolve_digital_link`라는 MCP 도구 하나로
수렴한다**: linkset 조회(digital_link_explorer.py:509)도, 후보 페이지를 하나하나 읽는
것(:682-686)도 같은 도구를 부른다. 도구들은 `explorer._tools` 딕셔너리에 캐시되므로
(:464-469), adapter가 **같은 이름의 로컬 도구를 미리 꽂아 넣으면** 끝이다:

```python
# adapter.py의 핵심 — 파이프라인은 평소처럼 도구를 부르는데, 답이 로컬 폴더에서 온다
async def local_resolve_digital_link(path: str) -> dict:
    # "/01/00000050457250?linktype=linkset" → entities/01-00000050457250/linkset.json
    # "/01/00000050457250/pages/pip.html"   → 해당 페이지 파일
    return read_from_fixture(corpus_root, path)

explorer._tools = {"resolve_digital_link": as_structured_tool(local_resolve_digital_link)}
```

- 문서 출처: `benchmark/entities/`(원본) 또는 `benchmark/counterfactual/`(변조본) —
  CF 실행은 corpus_root만 바꾸면 된다. (`data/raw/`는 벤치마크 제작용 캐시라 평가와 무관.)
- **이미지**: 이미지 링크는 별도 도구로 가는데 data URL을 받도록 돼 있으므로(:49),
  로컬 jpg를 base64 data URL로 변환해 전달한다.
- **인덱싱용 path 주입**: 파일 로더 `_read_bytes`(retrievers/vector.py:215)의 우선순위가
  bytes → **path** → href이므로, 로컬 도구가 돌려주는 linkset 응답에 각 항목의 로컬 절대경로를
  끼워 넣으면 인덱싱도 파일에서 바로 읽는다. 데이터셋 파일은 건드리지 않고 **응답 시점에**
  추가한다 (원칙 2 준수).
- 벡터 저장소는 **Neo4j 고정** (2026-07-10 팀 결정, Qdrant 미사용) — `neo4j_store`가
  `reset()`(:193)·`search_scoped()`(:119)를 모두 구현. KG와 같은 인스턴스 하나로 평가 전체가 돈다.

비유하면: **전화선을 끊고 우편함에서 꺼내게 하는 것.** 무엇을 가져올지 고르고, 읽고,
판단하는 머리는 전부 진짜다.

### 1.3 보조 실행 모드

- **fast 실행 (`--fast-miss`)** — miss에서 결말이 정해진 KG 헛걸음 구간을 건너뛰고
  문서 경로(external→수거→합성→critic_2)부터 돈다. critic_2 이후 재시도 라우팅은 코어의
  라우팅 함수를 그대로 사용. 건너뛴 구간의 시간은 full 표본에서 상수(α)로 실측해 TTFA에
  보정한다. 조기종료 진단은 관측 불가 → full로 도는 빠른 점검 30문항이 겸한다. (doc 05 §1)
- **직접 조합 모드 (개발용)** — v2의 방식(reset → 인덱싱 → 검색 → 합성만). critic·external이
  빠져 싸고 결정적이라 스모크/디버깅에 쓴다. 공식 수치에는 쓰지 않는다.
- **instant 모드 (관찰용)** — 코어 자체에 있는 KG 전용 즉답 경로(state_graph.py:169-182,
  critic 없음). hit 케이스의 "제품이 제공하는 또 다른 얼굴"이므로, hit 측정을 agent 모드로
  할지 instant도 병기할지는 팀 확인 (§9).
- v1에서는 답변 후 백그라운드 KG 적재(`_schedule_kg_builder`)를 **건너뛴다**
  (`graph.ainvoke` 직접 호출이라 자연히 안 탄다) — hit 상태는 §2.1의 ingest_kg.py로
  통제해서 만든다. 채점하려면 KG에 뭐가 들어갔는지 알아야 하기 때문.

## 2. 실행 매트릭스

실험 축 3개: **QA 범위**(스캔 세션/카탈로그) × **KG 상태**(miss/hit) × **문서셋**(원본/변조).

| 모드 | 무엇을 재현하나 | 대상 QA |
|---|---|---|
| **스캔 세션** (공식 수치) | 상품 하나를 스캔하고 질문: 엔티티마다 검색 DB를 비우고(`vector.reset()`) → 그 엔티티의 질문들을 순서대로 `graph.ainvoke()` | single-hop 216 |
| **카탈로그** (hit 전용) | KG에 20개 엔티티가 전부 쌓인 상태에서 여러 엔티티에 걸친 질문 | multi-hop 5 (별도 지표) |

카탈로그 모드가 hit 전용인 이유: 멀티홉 질문("부산의 명소 중 월요일 휴무는?")에는 스캔한 상품이
없다 = digital_link_path가 없다 → 그래프 구조상 external 경로가 건너뛰어진다
(external_retriever.py:87-90). 즉 **실제 제품에서 멀티홉은 KG로만 답할 수 있고**,
miss 상태의 멀티홉은 "모른다"가 정상 동작이다. (원하면 miss 상태의 카탈로그 모드를 돌려 정말 "모른다"로
답하는지 확인하는 건전성 체크로 쓸 수 있다.)

| KG 상태 | 준비 | 기대 경로 |
|---|---|---|
| **miss** | KG 비움 (또는 미접속) | KG 헛걸음 → external 경로 → 문서 기반 답 |
| **hit** | `ingest_kg.py`로 facts.jsonl → Neo4j 적재 (§2.1) | retrieve_kg_1 → synthesize_1 답으로 종료 |

"기대" 경로인 이유: 실제 경로는 critic이 정하며, 기대를 벗어나는 비율 자체가 지표다 (§4.4).

유효한 조합과 목적:

| 조합 | 목적 |
|---|---|
| **miss-original** (스캔 세션) | **공식 정확도·검색·TTFA** (첫 질문 상황, v1의 중심 수치) |
| **miss-counterfactual** (스캔 세션) | 진짜 읽고 답하는지 검증 (발산 대상 72문항만, §4.3) |
| **hit** (스캔 세션) | KG 경로 정확도 + critic의 KG답 수락률 + **miss 대비 TTFA 격차** |
| **hit** (카탈로그 — 멀티홉 5) | 멀티홉 (KG의 관계 질의 강점) |
| hit × 변조본 | **v1 제외** — KG값과 문서값이 어긋나는 stale 시나리오는 phase 2 |

개발 중 빠른 반복은 reset 대신 `search_scoped`(retrievers/vector.py:588)로 범위만 좁혀도
되지만, **공식 수치는 반드시 reset 방식**으로.

### 2.1 KG 적재 (`ingest_kg.py`)

- facts.jsonl → 파이프라인 KG 스키마(kg.py의 노드 8종, 허용된 predicate 목록)로 **매핑**해 적재.
- **매핑표는 평가 시스템 쪽에 둔다** — 데이터셋은 KG 스키마를 몰라야 한다(설계서 원칙 7).
  KG 스키마가 바뀌면 이 매핑표만 고친다.
- 매핑 방침: 영양성분·운영시간처럼 "엔티티의 속성"인 팩트 → 엔티티 노드의 속성으로,
  brand·located_in_region처럼 "엔티티끼리의 관계"인 팩트 → 노드 사이의 관계로.
  **매핑표는 KG 스키마 담당 팀원의 리뷰를 받아 확정한다** (§9).
- 적재 검증: `query_entities`로 20개 엔티티 왕복 확인 + 팩트 스팟체크. 추가로 §4.4의
  hit 지표들이 적재 품질의 간접 검증이 된다 (KG답 거부율이 높으면 매핑이 나쁜 것일 수 있음).

## 3. QA 루프 (스캔 세션 모드 의사코드)

```python
prepare_kg(kg_state)                      # miss: KG 비움 / hit: ingest_kg.py로 적재
install_local_tool(corpus_root)           # §1.2 — resolve_digital_link를 로컬 도구로 교체
for entity in entities:                   # 20회
    vector.reset()                        # 검색 DB를 비움 = 새 스캔 세션
    for qa in qa_of(entity):
        state = await graph.ainvoke(      # 진짜 파이프라인이 통째로 돈다
            initial_state(qa.question, digital_link_path(entity)))
        record(qa, state)                 # 답변 + usage_metrics(시간·토큰)
                                          # + critic 플래그·실제 경로 + 검색 결과·읽은 페이지

grade_all(records)                        # 채점 LLM은 루프 밖에서 일괄 (실행/채점 분리, §4)
```

- **루프가 이렇게 짧은 이유**: 인덱싱·검색·합성·critic이 전부 그래프 안에서 일어나고,
  시간·토큰 계측도 코어의 metrics.py가 `usage_metrics`로 다 해준다. 평가 시스템의 몫은
  로컬 도구 설치, reset, 그리고 **문항이 끝날 때마다 state에서 기록을 꺼내 저장하는 것**뿐.
- 질문마다 그래프가 처음부터 돈다 = 실서비스와 동일 (매 질문이 전체 경로를 지불).
- 직렬 실행 (동시에 돌리면 시간 측정이 서로 오염된다). critic 재시도 때문에 문항별 시간
  분산이 크다 → 반복 실행과 p50/p95로 흡수 (§5).
- 카탈로그 모드는 reset 없이 (KG만 사용) 멀티홉 5건.

## 4. 채점 — 3종 + critic 진단

### 4.1 답변 정확도 (LLM 채점관)

- 입력: 질문 + 정답(`gold_answer`) + 정답 근거 팩트의 값 + 시스템의 답변. temperature 0.
- 판정: `correct / partial / incorrect` + 한 줄 근거. 숫자는 반올림·단위 표기 차이를 허용
  (QA 검수 때 확인한 허용오차 사례가 qa.jsonl에 남아 있음 — 채점 프롬프트에 규칙으로 명시).
- 채점 모델은 파일럿에서 확정. 기본 방침은 **파이프라인과 다른 모델** — 자기가 만든 답을
  자기가 채점하면 후해지는 편향을 피한다.
- 진행형 답변("추가 소스를 확인하고 있습니다")이 최종 답으로 남은 경우는 `incorrect`가 아니라
  **무응답**으로 따로 센다 (실패 유형이 다르므로).

### 4.2 answer_page_hit — 정답 페이지를 찾았는가 (결정적 판정, LLM 불필요, miss 전용)

- manifest에는 "이 팩트는 이 페이지에 인쇄됐다"는 기록(placement 맵)이 있다.
  실행 state에 남은 **읽은 페이지 목록**(traversed_links·벡터 검색 결과·used_sources)과
  대조하면 LLM 없이 기계적으로 적중 여부가 나온다.
- **목적은 점수가 아니라 실패 원인 분해다.** 답변 정확도와 조합한 4분면:

| 정답 페이지 | 답 | 진단 |
|---|---|---|
| 읽음 | 맞음 | 정상 동작 |
| 읽음 | 틀림 | **읽기/합성 실패** — 문서는 눈앞에 있었다 |
| 못 읽음 | 틀림 | **검색/후보선택 실패** |
| 못 읽음 | 맞음 | **요주의** — 문서 없이 맞혔다 = 외운 답(사전지식) 의심 → §4.4 조기종료와 교차 확인 |

- 이미지 QA의 정답 페이지 = 해당 media 파일.
- KG-hit 케이스의 대응 지표는 **kg_fact_hit**: retrieve_kg_1 결과에 정답 근거 팩트의 값이
  들어 있는가 (넣은 팩트를 얼마나 잘 꺼내는가).

### 4.3 CF 발산 — 진짜 읽고 답했는가 (두 실행 결과의 대조, LLM 재호출 없음, miss 전용)

같은 질문을 원본 문서셋과 변조 문서셋에 각각 던지고 답을 비교한다.
**변조본 실행은 발산 대상 72문항만 돌린다** (2026-07-13 결정, doc 05 §0) —
정답 근거 팩트가 변조되지 않은 문항은 두 문서셋에서 같은 답이 날 수밖에 없어 제외하고,
근거가 변조된 이미지 QA 2건은 사진(원본값)과 페이지(변조값)가 원리적으로 모순이라 제외.

- **발산 대상 72문항** (html QA 중 정답 근거 팩트가 변조된 것, 20/20 엔티티 커버). 판정 3종:
  - **발산** — 원본에선 원본값, 변조본에선 변조값으로 답이 **갈림** = 문서를 읽고 있다 ✅
  - **사전지식 활용** — 변조본에서도 원본/실세계 값을 답함 = 문서 대신 학습 때 외운
    지식으로 답했다 ❌ (§4.4의 조기종료와 대조하면 "안 읽고 답함"인지
    "읽고도 무시함"인지 갈라진다)
  - **둘 다 오답** — 발산 판정 불가 → 정확도 문제로 분류
- 판정은 대부분 기계적 값 대조(답에 원본값이 있나 변조값이 있나)라 답변 표현이 흔들려도
  잘 뒤집히지 않는다. 다만 재검사·대조군 기준선 없이 가는 선택이므로, 사전지식 활용률을
  보고할 때 "실행 간 답변 변동이 일부 섞였을 수 있음"을 한계로 한 줄 명시한다.

### 4.4 critic 행동 진단 (신설 — v3)

critic의 판단은 LLM 출력이라(critic.py:16-36) 양방향 오판이 가능하고, 이것이 곧
실서비스 품질의 일부다. 문항마다 critic 플래그(go_to_kg / external_retrieval /
go_to_generate / failure_reason)와 **실제로 탄 경로**를 기록해서 집계한다.

이 기록에 새 계측은 필요 없다 — critic 판단은 이미 최종 state에 담겨 FastAPI 응답으로도
노출되는 필드들이고(ChatResponse, apps/schemas/chat.py:17-37: critique·플래그 3종·
failure_reason·재시도 카운터 3종·critic_stage), 실제로 탄 경로는 `usage_metrics["nodes"]`에
쌓인 노드 실행 이력에서 그대로 복원된다.

| 지표 | 뜻 | 왜 중요한가 |
|---|---|---|
| **조기종료율** (miss) | external에 안 가고 critic_1에서 끝난 비율 | 합성기가 사전지식으로 답을 지어내고("MUST NOT use prior knowledge" 지시 위반, prompts.py:335) critic_1이 "답이 적절하면 통과" 첫 규칙(:428)으로 수락한 것. **문서를 한 장도 안 읽고 답한 것**이므로 원본 문서셋에선 맞아 보여도 신뢰 불가 — 변조본 실험에선 "사전지식 활용"으로, 4분면에선 "못 읽음·답 맞음"으로 잡힌다 |
| **KG답 거부율** (hit) | KG에 정답 팩트가 있는데(kg_fact_hit ✓) critic_1이 external로 보낸 비율 | KG 캐시가 있어도 활용을 못 하는 것 — hit의 속도 이득이 사라진다. 원인 후보: KG 결과가 entity 중심 형식이라 값이 속성 속에 묻혀 critic이 "유용한 정보 없음"으로 오독 |
| **경로 혼입율** (hit) | hit 실행인데 최종 답의 근거가 벡터 문서인 비율 | hit 정확도를 해석할 때 "KG로 답한 정확도"와 분리해서 보고해야 함 |
| **재시도 분포** | go_to_generate/go_to_kg/external 재시도 횟수 (상한: state_graph.py:103-121의 max attempts) | 시간 분산의 주범 — TTFA p95와 같이 읽는다 |

이 지표들은 **점수가 아니라 진단**이다 — 벤치마크의 점수는 최종 답변에 대해서만 매기고
(4.1~4.3), critic 진단은 파이프라인 개선의 재료로 팀에 전달한다.
과거에 규명했던 "critic_1이 엔티티가 KG에 있다는 것만으로 정보가 있다고 오판"하는 경향이
hit 케이스에서 재현되는지도 여기서 관찰된다.

## 5. 시간 측정 프로토콜

**타이머를 만들지 않는다.** 그래프의 모든 노드가 `ObservedNode`로 감싸져 있어(§1.1),
문항이 끝나면 `usage_metrics`에 노드별 시간·LLM 호출별 시간·토큰·전체 경과가 다 들어 있다.
평가 시스템은 그걸 꺼내 저장할 뿐이다.

- **TTFA** = `pipeline_elapsed_ms` (질문 → 최종 답). 실서비스 사용자가 기다리는 시간 그대로.
- **분해** = 노드별 latency: miss의 "KG 헛걸음"(retrieve_kg_1 + synthesize_1 + critic_1),
  external 경로(후보 선택·페이지 읽기·인덱싱·검색), 합성, critic.
- **miss vs hit TTFA 격차** = "첫 질문 vs KG가 쌓인 뒤 질문"의 차이 — KG 가치의 헤드라인 수치.
- **검산 자동화**: 전체 경과 ≥ 노드별 합 — 부등식이 깨지면 계측 누락이다.
- **캐시 채움/비움 분리**: 이미지 설명 캐시(`.vlm_cache.json`)가 차 있으면 인덱싱이 훨씬
  빠르다. 기본은 캐시를 채운 상태로 재고, 캐시 빈 상태(첫 스캔 재현)는 엔티티 2~3개만
  격리해서 잰다.
- 반복 3회(기본), 직렬 실행 → p50/p95 보고. critic 재시도 때문에 분산이 크므로
  평균이 아니라 **분위수로** 말한다. 병렬 실행 금지.

## 7. 비용 통제 (그대로 실행 순서이기도 하다)

실그래프 실행은 문항당 LLM 호출이 v2 설계보다 많다 (miss 기준: 합성 2회 + critic 2회 +
후보 선택 + 이미지 분석 + 채점). **사전 어림보다 파일럿 실측이 우선**이다.

| 단계 | 규모 | 목적 |
|---|---|---|
| ① 파일럿 | 5문항 (miss, 캐시 채움) | 문항당 토큰·비용 실측, 채점 모델 확정, 경로 로그 눈검사 |
| ② 빠른 점검 셋 | 30문항 고정 (문서/이미지·언어·엔티티가 골고루) | 개발 중 반복 실행용, 회귀 확인 |
| ③ 본실험 miss | 원본 216 + 변조본 72 (캐시 채움) | 공식 수치 + CF |
| ④ 본실험 hit | 221문항 × 원본 (캐시 채움) | KG 경로 + miss 대비 격차 + critic 진단 |
| ⑤ (선택) 캐시 빈 상태 측정 | 엔티티 2~3개 격리 | 첫 스캔 TTFA 수치만 별도 — 필요 시 |

**메인 실험은 ③-a·③-b·④ 세 개다** (2026-07-13 결정) — ⑤와 반복 실행은 선택 항목.

- 정확도 실험은 전부 **캐시를 채운 상태**(VLM 캐시 유지)로 — 사진 설명은 같은 입력이면
  같은 결과라 정확도에는 영향이 없다. hit 실행은 critic_1이 수락하면 그래프가
  일찍 끝나므로 miss보다 싸다 — 단 KG답 거부율만큼 external 비용이 추가된다 (§4.4).
- ①에서 실측한 문항당 비용 × 규모로 ③④⑤ 견적을 다시 내고, 본실험 전에 승인받는다.
- **구체 수치는 doc 05 (실험 규모·비용·시간 계획)** — 2026-07-13 파일럿 실측 기준
  메인 실험 3개(③-a·③-b·④): LLM 호출 ~2,500회 / 비용 ≈ $6.1 (공식 단가 확인, 자동
  프롬프트 캐시로 실비는 더 낮을 수 있음) / 직렬 ~1시간 + 채점 15분 (miss는 fast 실행,
  doc 05 §1). 멀티홉 5문항은 hit 전용(§2)이라 miss 실행은 216문항, 변조본 실행은
  발산 대상 72문항만(§4.3)이다.
